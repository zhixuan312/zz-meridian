# Testing

This page is the testing standard: the kinds of test, the three tiers, when each runs, and the rules a red, a limit and a release follow. An adopted or created project follows it, Meridian follows it, and a spec cites it rather than restating it.

## The kinds

A check has one size and one type. The two are independent: a size never says what a check checks, and a type never says what it costs.

**Size** is what a check needs to run, not what it intends.

- `static`: reads files, with no test runner and no process of its own beyond the tool (the token and registry checks, the specification checks, contrast, route types, types, lint).
- `small`: one process, in the test runner, with no child process, no server, no browser and no build.
- `medium`: starts processes or servers on this machine, with no browser.
- `large`: needs a real browser or a production build.

Size sets the cost, so it sets when a check can run: the smaller it is, the earlier and the more often.

**Type** is what a check checks.

- `functional`: does it do what it should (a control works, a page reaches its data, a function returns the right value).
- `non-functional`: a quality other than speed (accessibility, contrast, layout and overflow, sizes and bytes, route policy, the safety of the data a run can reach).
- `performance`: time behaviour against a budget (navigation budgets, live-data bounds, the Web Vitals floors).

Type sets whether a run needs a quiet machine: a performance check measures the machine as well as the page, so only a performance check needs one. Regression is not a type: it is why a change is checked.

## The tiers

A tier is what a piece of work is for, and it decides which command proves it. There are three, in the order a piece of work is planned.

- **Tier 1: make it work.** The agreed result works, completely: every page opens and nothing breaks, every function is there and works, all the content is there, and every element a person can use by mouse, touch, keyboard or screen reader does. Functionality, data integrity, migrations, auth and access boundaries, contracts, compatibility, and any agreed operating requirement. Content the user cannot see or reach at all counts as missing; content that is cut but still visible is the look, below. Its tests prove the result; a Tier 1 phase uses `pnpm test:t1`.
- **Tier 2: make it work well.** It already meets the requirement and becomes better to use, in ways the user can see or feel: speed, latency, efficiency, smoothness, and how it looks — beauty, layout, a line cut but still visible, a small target, low contrast. Tier 2 is measured and reported, never a red: a value past its line is a warning with its numbers, and a finding is named in the closing line, the run continues and exits 0, and every run records its values for the next release to compare against. A Tier 2 phase uses `pnpm test:t2`.
- **Tier 3: build to last.** The code is easy to maintain and change, and the user cannot tell the difference: standards, clear implementation, confirmed-dead code removed, reuse where a concrete need exists. Lint and the type check are Tier 3 — they run and report and never block, and a build that does not compile is not a lint finding: the app cannot open, so it fails Tier 1 through the build. There is no Tier 3 test suite; a Tier 3 phase uses `pnpm test:t2`, so whatever it preserves is still proven. Tier 3 work must preserve agreed behaviour, and its effect on performance is measured and reported like any other change.

**Only Tier 1 turns a run red.** A run never stops at the first failure: it runs every stage and names every finding at the end, with the Tier 2 and Tier 3 findings in their own part of the line — `reported, not failed` — so one red never hides them. One function decides which of the two lists a failing check joins (`record` in `scripts/lib/summary.ts`), and the audit's own findings are sorted by the same rule (`scripts/lib/audit-findings.ts`).

There are exactly three test commands, and none takes an argument. The tool picks the tests.

| Command | Runs |
|---|---|
| `pnpm test:t1` | The Tier 1 tests affected by the changes since the last green run, eslint over the source files the change touches, and the type check. Lint and the type check report. |
| `pnpm test:t2` | The affected Tier 2 checks, and the affected Tier 1 tests with them, including the browser function sweeps. |
| `pnpm test:release` | Every Tier 1 and Tier 2 test, once, plus the browser function sweeps, the timed browser suites, lint and the type check. Lint and the type check report. |

**Selection.** Vitest's `related` reads the import graph and runs the tests that reach a changed file; a changed test file is run itself. A document has no import edge, so the tests that name it are its group (`git grep` over `tests/`): `docs/testing.md`, for example, selects the guards that read it. A change that reaches no test at all runs the whole tier, and so does a deleted source file, whose importers can no longer be computed: an import graph that knows nothing about a file is not evidence that nothing needs checking. The static checks (the tokens, the registry, the specifications) read the whole tree and run on every tier; contrast is one of them and is Tier 2.

**Tier 2 is a convention, never a list kept by hand.** `*.perf.test.ts(x)` is Tier 2 in any repository. This repository's timed browser suites are Tier 2 as well: navigation judged against its budgets, live data and the Web Vitals floors (`scripts/browser.ts --depth timed`), and the 20-sample protocol (`--depth perf`), which has a stage of its own — `node scripts/test-run.ts stage perf` — and is never asked for by a gate. Their values — the navigation budgets, LCP, INP, CLS and dropped frames, the p95s — are reported with their numbers and never fail a run: a red is Tier 1 alone. A timed or perf suite that prints FAIL is counted in the closing line as over budget (reported, not failed). `test:t2` reports the timed suites not run: `test:release` runs them alone on a quiet machine. Every other test under `tests/` is Tier 1. `test:t1` never runs a Tier 2 check. A repository with no `*.perf` test still has `test:t2`, and it runs the affected Tier 1 tests.

**The browser function sweeps are Tier 1, and the audit inside them sorts its own findings.** `scripts/browser.ts --depth fn` audits every page at six widths in both themes, presses every control, walks every keyboard stop and the rail, runs the personas and the journeys, the assistant absent and walk-through states, the product's own `browserChecks` and the size caps. A page that answered an error, content that cannot be seen or reached at all, a control that does nothing, an element a person cannot use by pointer, keyboard or screen reader — each fails the run, whatever the technique. What the audit finds that is there and works and is awkward — a target under 44px, low contrast, text cut but still visible, a page that scrolls sideways, a heading that skips a level, a card that scrolls on its own — is Tier 2: it is printed under `reported:`, counted in the run's closing line, and exits nothing. `scripts/lib/audit-findings.ts` is the sort, in one place. They need a production build and Chrome, so they run where those exist: `test:t2`, `test:release` and the release workflow's sweep jobs, selected for a change that can alter what a page draws or a control does. `test:t1` never runs them. `--only <audit|interactions|keyboard|rest>` runs one sweep against the same assistant-on server, which is what a release sweep job does.

`tests/deep-*.test.ts(x)`, the large browser-fixture suites of the checks, are Tier 1: they verify a check script's function, not a quality beyond the requirement. Their size, not their tier, keeps them out of the main Vitest run; they run as their own stage when a script, a journey or one of their own files changed, and `test:release` always runs them. In the release workflow `node scripts/test-run.ts stage deep --since <ref> [--part i/n]` runs only the deep tests the changes since the previous tag reach, and all of them when `scripts/`, `journeys/` or a deep test changed. `stage <static|sweep <name>|deep|tier2>` runs one part of `test:release` for a CI job; it is not a fourth test command.

**A change is linted and type-checked as it is checked, and neither blocks.** `test:t1` runs the same eslint `test:release` runs (linting the whole repository) over the source files a change touches, and the type check beside it. Both are Tier 3: the run prints what they found as `reported, not failed` and exits 0. A lint error once reached master through a run that checked types but never linted (the drawer's `react-hooks/refs`, `b54c5d7b`), and the answer was to run it here, not to make it a gate on a change nobody has finished. Compilation is still Tier 1: `next build` fails on anything that cannot compile, and the build runs in `test:t2` and `test:release`. Documents and generated output are left out (`lintTargets` in `scripts/lib/lint.ts`).

**Last green.** After a passing run the command writes the commit it proved to `out/last-green`, which is gitignored, and reads it before the next run. That keeps a per-change run to the diff since the last green, not the branch's whole history. A missing marker falls back to the diff against master. A checkout with neither a marker nor a diff (master itself, a fresh CI clone) runs the whole tier, because no green run is evidence for it. `test:t1` leaves the marker alone when the change also needs what only `test:t2` runs (a Tier 2 check, or the browser sweeps, which need a build and Chrome), so `test:t2` is not skipped by the run before it. A Tier 2 value over its line does not hold it: the run is a pass that reported.

**A red run hands the next one its failures.** A run that ends red leaves `out/last-run.json`: the tree it proved, and the test files that failed. The next run starts from that tree, so a fix runs the failures it answers, the tests its own change reaches, and the static checks, lint and type check its change touches — the smallest set that proves the fix and protects what it touched, not everything since the last green run. A tree that has not changed since the red run may be retried once, and that run reports itself as a retry and never advances the marker: a pass with no cause named is flaky, and a flaky Tier 1 check is a red under `Fixed means`. A second run of the same bytes is refused, and asks for the cause from the output first.

A run that needs Chrome reports `not run` with the reason where it is absent, and never `ok`: this repository's `tests/deep-*`, the browser sweeps, the timed suites and the Postgres suite with no service URLs. Nothing that did not run is reported as passed, and a run with something not run does not advance the marker.

**A not-run is either evidence missing or a project's own configuration.** Absent Chrome, absent service URLs and a browser that did not start are missing evidence: the check is reported not run with the reason and the run does not advance the marker, because a later run on a machine that has them can. A case a project leaves unrun by its own configuration — a rail route with no navigation check, a prefetch cap that is not its promise because its rail is not in a drawer on a phone (`scripts/navigate.ts`), a size baseline the project inherited from the release instead of recording its own (`sizeBaselineOwned` in `scripts/lib/sizes.ts`), or a build that writes no `renderingMode` because the project's Next config sets neither `cacheComponents` nor `partialPrefetching`, which the route policy presupposes (`scripts/route-policy.ts`, as an update's finalize already reports it) — is reported not run with the reason on every run, never as a pass, and does not hold the marker: a rerun can never change it, and holding it would rerun the whole tier, browser sweeps included, on every run of every project that has not configured navigation. `declaredNotRun` in `scripts/lib/coverage.ts` draws the line; `scripts/browser.ts` reports such cases under `declared`, and `scripts/test-run.ts` prints them as `not run (declared by the project's configuration)`.

## When each runs

A moment is when a person or an agent runs a command. CI runs the same commands at the same moments.

- **While editing**: `pnpm test:t1`, or a narrowed run of the file changed, `pnpm exec vitest run <file>`, and a look at the page with `node scripts/shot.ts <route> --width 1440,390 --theme dark,light`.
- **After a change** (one complete logical change that can be verified on its own, in any tier): `pnpm test:t1` and the tests the change affects. For visible behaviour, exercise the flow or state that changed, and run `pnpm test:t2` when the change can alter what a page draws or a control does.
- **After a Tier 2 or Tier 3 phase**: `pnpm test:t2`. A change under `cli/` or the update flow also runs the consumer smoke's update half (`--adopt --update --verify`), and any other `scripts/` change its verify half (`--adopt --verify`), both with CI's flags — `CI=true` — so the path an adopter walks is proved before the push, not by the scheduled run hours later.
- **Before a release**: nothing is run locally beyond the checks of the change itself and, when a change reaches `cli/`, the consumer smoke. The release workflow's jobs are the proof, each check once on its own runner. A later relevant change makes part of that evidence stale; re-run only the tests it affects.
- **On a schedule**: `pnpm test:release` on master's current commit, with the Postgres services configured, in `.github/workflows/weekly.yml` (Meridian's repository only). A marker is absent in a fresh CI clone, so the run covers the whole tier. The 20-sample protocol runs there as its own non-blocking step, `node scripts/test-run.ts stage perf`. The weekly consumer job runs a created dashboard's whole `test:release`.
- **Meridian's release** (`.github/workflows/release.yml`, dispatched from master; Meridian's repository only): one job per check, each run once. `static` (lint, the type check, every Vitest file but the browser-fixture tests), `sweep-audit`, `sweep-interactions`, `sweep-keyboard` and `sweep-rest` (the Tier 1 function sweeps), `deep` (the browser-fixture tests a change since the previous tag reaches, in two parts) and `consumer` (the tarball adopted, created and updated from the release before; the created dashboard runs `test:t1`, a production build and the rest sweep) block `publish`. `tier2` (the timed suites) and `perf` (the 20-sample protocol) run beside them with `continue-on-error`: it never blocks the publish or the tag, and `tier2-attach` puts its record and table on the Release after the tag. The release publishes and tags last.
- **An update's finalize** (`update --finalize`): `pnpm test:t1` — the Tier 1 tests affected by the change, the static checks and the type check — then a production build and the build's own checks in the project. Two of those judge the project, not the release, and are reported `not run` with the reason — never counted as passed and never failed — when the project cannot supply what they read. `node scripts/route-policy.ts` is not run when the project's Next config does not set both `cacheComponents` and `partialPrefetching` (a project with no config has neither): the route policy reads the prerender modes only those flags make a build write, and an adopted project keeps its own config, so an update never switches its rendering on to get a green finalize. `node scripts/sizes.ts` is not run unless `scripts/verify.baseline.json` is the project's own — the team recorded it (`node scripts/sizes.ts --write-baseline` stamps `recordedBy: "sizes.ts"`) and it differs from the release's — because a created project inherits the release's baseline, and a product with pages of its own would otherwise be judged against figures that are not its. It does not run `test:release`: the browser sweeps and the timed suites belong to the team's own release before it ships, and a finalize that ran them cost over an hour on a 4-CPU runner (run 42600180906) for every adopter's update.
- **An update's finalize time** is a Tier 1 operating requirement, guarded by the consumer smoke (`cli/scripts/smoke.ts`): each case's finalize wall time is recorded, and a case over its limit fails the run. An adopted origin has no shipped tests, so its finalize is the static checks, the type check and the build: 0.38.0's own finalize ran that scope in 37.0 s on the 4-CPU release runner (its build 13.8 s of it, run 42600180906), and the case keeps the 90 s limit it was already held to — kept, not loosened. A created origin has only the team's starting examples, so its finalize is `test:t1` on those, the type check and the build, and it is held to `FINALIZE_CREATED_LIMIT_MS`, 240 s. Measured locally on Node 26 with the two build checks reported not run for the adopted origin: the adopted 0.38.0 origin finalized in 15.1 s (`tests 6.9s · build 6.5s`), and a created one with the template's whole Tier 1 set, whose config sets the flags so the route policy ran, in 46.0 s (`tests 30.4s · build 13.0s · route-policy 0.2s`). A finalize that grows past its limit is red in the release's `consumer` job before it reaches an adopter, and raising a limit takes the owner's decision like any other limit.

## Local runtimes

The browser suites need a Chrome executable, which `CHROME` may name, including official `chrome-headless-shell` for unattended runners. Downloads are explicitly directed into each temporary profile's own `Downloads`, never the user's default folder.

The Postgres suite the skill's references hand a team lives in `scripts/fixtures/postgres/` and needs `MERIDIAN_POSTGRES_URL`, `MERIDIAN_POOLER_URL` and `MERIDIAN_PG`. `pnpm test:release` runs it where those are set and reports it **not run** with the missing names where they are not; it is never reported as passed.

## Rules

- **Behavior, not pins**: assert user-visible meaning, transitions, boundaries and errors, not source snippets, prose, utility classes, incidental defaults, wiring or byte copies. Remove incidental pins rather than repinning them; retain meaningful behavior, accessibility, security, architecture and planted-validator cases.
- **Observer readiness**: the interaction check waits for its mutation observer to attach before sending input. Elapsed timer delays are not proof that a busy renderer has armed it.
- **Asynchronous state**: wait for the state under assertion. A neighboring live-region message is not proof that the state under test has settled.
- **Standalone gates**: preserve the Node-built-in-only dependency boundary.
- **Isolated effects**: reset observed state between tests and settle the callback created by that test, not a stale callback left by an earlier case.
- **Owned resources**: temporary fixture folders are removed after each case. A child-process readiness wait reads complete output across chunks, rejects on spawn failure or early exit, and the owning case waits for shutdown in its cleanup.
- **Quiet machine**: A run needs a quiet machine exactly when it runs a check whose type is performance: no other build, browser or test run.
- **Fixed means**: every red is fixed in the product or in the check, never by skipping, narrowing or deleting the check. A limit moved under `## Budgets` changes a value, never what is measured.
  - A red is fixed when its cause is named and a test that failed on the old code passes, at the lowest layer that can show it.
  - A measurement no test can reproduce (a time, a dropped frame) is fixed after three consecutive passes on a quiet machine. One pass of a measurement is not evidence.
  - A red whose cause is not named after a run narrowed to its route or page, with the render instrumented, goes to the owner as a decision, with what was measured, before any limit is touched.
- **Limits, and the flag line**: every Tier 2 value is judged against the release before, and reported; every run records each value (per tap, per sample) in `out/perf-record.json`, and ends with one table sorted by change: check, page, baseline → now, change. A timing is flagged at +25% and at least +10 ms, an LCP-scale value at +25% and at least 0.1 s, CLS at +0.05, a size at +5%; improvements are listed too. Once three releases are recorded the line comes from their measured spread instead — outside mean ± 2 sd with `max(sd, 5% of the mean)` as the spread's floor, and the same minimum move — and the flag is a report, never a failure. `scripts/perf-history.json` holds the last five releases; a fresh checkout without it, or a project, uses the seed (today's budgets as values) and says so. A baseline older than the previous release warns. Nothing in this section blocks a run; isolating a flagged value to one commit is a manual before-and-after step, never a bisect tool. The budgets in `## Budgets` are the seed and the yardstick, not limits a run enforces. A check's own functional bound is not a Tier 2 value: a change that never arrives, a page that never becomes ready, a control that never answers or a link that never responds is a red under a fixed, generous bound (`PATIENCE`, `HANG_BOUND_MS`, `LINK_HANG_GUARD_MS`), never under a budget; how long a real answer took is the Tier 2 value, recorded and reported like any other measurement.
- **Once per commit**: evidence recorded on a commit stands for it and for any later commit whose difference touches none of the command's inputs. A command is run again only when its record is missing, its inputs changed, its record disagrees with what was reported, or it is in concrete doubt.
- **Flaky is red**: a Tier 1 check that fails sometimes is a red under `Fixed means`; a retry that passes does not clear it. A Tier 2 value that jumps without a code change is reported like any other, and investigated from the table.
- **Releases**: a release is the release workflow's jobs passing on the commit being released; Tier 2 is reported with the Release and never holds it. A red left at a release is the owner's decision, named in the release's changelog as a known issue with where it is fixed. A command's inputs are the scripts it runs, the product code and its configuration, the package manifest and lockfile, every document a page renders, and, for a test command, the files its tests read.

## Basis

- **Sizes** by what a test needs, not what it intends: Google's small, medium and large (*Software Engineering at Google*, ch. 11, and the Google Testing Blog's "[Test Sizes](https://testing.googleblog.com/2010/12/test-sizes.html)", 2010). Meridian adds `static` for a check that runs no test at all, and counts a browser or a production build as `large`.
- **Tiers** as stages: fast checks per change and slower stages before a release, in one pipeline (Humble and Farley, *Continuous Delivery*, 2010).
- **Proportions**: many fast tests and few slow end-to-end ones ("[The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)", Ham Vocke, 2018).
- **Types** after the ISTQB glossary and ISO/IEC 25010. Meridian lifts performance out of the non-functional qualities into a type of its own, because it alone needs a quiet machine, and does not count regression as a type.
- **Measurement**: performance judged by percentiles of repeated samples on a quiet machine, the phone after Lighthouse's mobile throttling.
- **Flakiness** as a defect: a test that passes and fails on the same code erodes trust in every result (*Software Engineering at Google*, ch. 11 and 14).

## The classification

Every test belongs to exactly one tier, by the convention alone: a file matching `*.perf.test.ts(x)` is Tier 2, and every other test under `tests/` is Tier 1 — `tests/deep-*.test.ts(x)` included, whose size keeps it out of the main run, never its tier. `tests/cli-*` is Meridian's repository only (the package's own tests; a project made from Meridian has no `cli/`). A created project receives none of Meridian's tests: only `tests/setup.ts` ships and is Meridian's, and `tests/examples/` ships as the team's starting point; every other test in the project is the team's. The static checks run on every tier because they read the whole tree.
